# AEP: Alerting — webhook notifications on service-health transitions

- **Date:** 2026-07-19
- **Author(s):** Berny ryders
- **Status:** Accepted

## Summary

Add an **alerting** module: a background evaluator in the hub watches
service-health status and fires a **generic webhook** when a rule's target (a
group, service, or tier) crosses into a bad state and stays there for a
configured duration — and again when it recovers. Rules and channels are
**config-defined** (a hot-reloadable ConfigMap, exactly like the health
module's `serviceGroups`); alert **state** persists in ClickHouse so restarts
don't re-fire or drop resolves. This is the "notification subsystem avuru-obs
doesn't have yet" that both the [error-tracking](2026-07-16-error-tracking.md)
and [service-health](2026-07-18-service-health-groups.md) AEPs defer to. It is
the read-side status model those modules produce, turned into action.

## Motivation

Service health is computed but nobody is told. An operator sees a group go
`down` only if they are looking at the board. Alerting closes the loop: when
`payments` goes down and stays down, an on-call webhook fires — into Slack,
PagerDuty, Opsgenie, Alertmanager, or a custom endpoint, all of which accept
incoming webhooks. No app changes, no new signal: it acts on the RED-derived
health the platform already produces.

Ties to the [wedge](../AGENTS.md): reuses existing telemetry, no instrumentation.
Ties to the [locked decisions](../agent_docs/architecture.md#locked-decisions-and-rationale):
"the hub is never in the telemetry **byte-path**" is about telemetry ingress —
a control-plane webhook is a different thing, but it *is* the hub's first
outbound-to-the-world call, so it is treated as a security surface (§Outbound
delivery). Evaluation is a background ticker, the same shape as the health
config reloader; state persistence follows error-tracking's triage precedent.

### Goals

- Config-defined **rules** (`alerting.rules`) and **channels**
  (`alerting.channels`) in a hot-reloadable ConfigMap — edit + `kubectl apply`
  or `helm upgrade`, no restart. Fail-loud validation like `modules.Parse`.
- A rule fires when its target's health matches a condition (`down` |
  `degraded` | `not-healthy`) sustained for a `for` duration, and resolves when
  the condition clears. Fire and resolve each deliver a webhook.
- Delivery behind a `Notifier` interface with one implementation for v1 — a
  **generic JSON webhook** — so Slack/email/etc. are drop-in later.
- Alert **state** and a short **history** persist in ClickHouse: restarts don't
  re-fire an already-firing alert or miss a resolve; the UI shows what's firing.
- Gated by the module framework (`modules.alerting.enabled`, default **true** —
  inert with no rules, so default-on delivers nothing until configured).
- A read-only `/alerts` UI: firing alerts, recent history, the configured rules.

### Non-goals (v1)

- **Triggers other than service-health** — RED-threshold and error-tracking
  conditions plug into the same evaluator later, but v1 fires only on health
  transitions.
- **Channels other than webhook** — native Slack/email formatters are deferred
  (`Notifier` makes them additive).
- **UI-created rules + auth** — rules are config only; "who may edit rules"
  wants the v0.2 auth seam. No write API in v1.
- **HA leader election** — evaluation assumes a single active evaluator (hub
  replicas default to 1). >1 replica would duplicate notifications; deferred and
  documented loudly.
- Silences / maintenance windows, alert grouping / inhibition, flap-rate limits
  beyond the `for` timer.

## Solution

A module declared in the [registry](../hub/internal/modules) and gated across the
usual layers. Unlike service-health it **owns a migration** (mutable state), and
unlike every prior module it makes an **outbound** call.

### Data flow

```
serviceGroups + alerting rules/channels (ConfigMaps, hot-reloaded)
        │
  [evaluator ticker in the hub] ── every ~30s, per tenant ──▶ health.Rollup(...)   (reuses hub/internal/health)
        │  compare current status to persisted AlertState (the `for` timer)
        ├──▶ Notifier.Send → webhook POST      (bounded retry, SSRF guard, secret redaction)
        └──▶ SaveAlertState + AppendAlertHistory (ClickHouse)
                        │
                 GET /api/v1/alerts[/rules] (read-only) ──▶ /alerts UI
```

The evaluator calls the `hub/internal/health` package **directly** (not the HTTP
API), so it needs only core RED; it shares the `serviceGroups` config for
group/tier targets.

### Components (hub)

- `hub/internal/alerting/config.go` — `Rule{Name, Selector(group|service|tier),
  When, For, Channel}`, `Channel{Name, Type:"webhook", URL, Secret}`,
  `Config` with `Parse`/`Validate`/`Default`. Fail-loud (unknown `when`, unknown
  channel ref, empty selector, bad URL). Mirrors `health/config.go`.
- `hub/internal/alerting/evaluator.go` — a **pure** function
  `Evaluate(report health.Report, prev State, now) → (State, []Notification)`.
  No I/O; the `for` timer and dedup live here, so the state machine is fully
  unit-testable. Deterministic and idempotent per tick.
- `hub/internal/alerting/notifier.go` — the `Notifier` interface + `webhookNotifier`
  (JSON POST, context timeout, capped exponential retry, SSRF guard, secret
  redaction in logs).
- `hub/cmd/hub/alerting.go` — background ticker wiring: hot-reload rules (mtime
  poll, like `groups.go`), evaluate per tenant, deliver, persist. Started only
  when the module is active; a single evaluator (see HA non-goal).

### Storage (`0008_alerts.sql`, module `alerting`)

- `otel.alert_state` — `ReplacingMergeTree(UpdatedAt)` keyed
  `(Tenant, RuleName, Target)`: `Status Enum8('ok','pending','firing')`,
  `Since DateTime`, `LastNotifiedAt DateTime`, `UpdatedAt`. The error-tracking
  `error_issue_status` precedent — newest row wins, survives restart.
- `otel.alert_history` — append-only `MergeTree`
  `ORDER BY (Tenant, FiredAt)`: one row per fire/resolve for the UI timeline,
  with its own retention TTL (`AVURUOPS_RETENTION_ALERTS_DAYS`, default 30).
- Store gains `LoadAlertStates` / `SaveAlertState` / `AppendAlertHistory` /
  `ListAlertHistory`, behind the `storage.Store` seam like every other query.

### API (read-only, module-gated)

- `GET /api/v1/alerts` — currently-firing alerts + recent history (tenant-scoped).
- `GET /api/v1/alerts/rules` — the loaded rules/channels (secrets redacted), so
  the UI can show what's configured without a write path.

### Alert lifecycle (per rule × target, each tick)

`ok → (condition true) pending(since=now) → (sustained ≥ For) FIRING [send fire]
→ (condition false) RESOLVED [send resolve] → ok`. State is persisted every
tick: a restart resumes mid-`for`, an already-`firing` alert is not re-sent, and
a resolve is delivered exactly once. Idle/unknown targets never fire (no signal
is not an outage — same rule as the health module).

### Outbound delivery (the new role — treated as a security surface)

The webhook is the hub's first outbound call. `webhookNotifier` enforces: a hard
request timeout; **capped** exponential-backoff retries (a down endpoint must not
back up the evaluator); an **SSRF guard on by default** — refuse loopback,
link-local, private, and cloud-metadata (169.254.169.254) targets unless the
operator sets an allowlist (self-hosted Alertmanager/Slack-proxy on a private
net is a real case, hence the override); and **secret redaction** — a channel
`secret` (sent as a signing header/bearer) never appears in logs or the
`/rules` API. Delivery failures are logged and retried, never fatal to
evaluation.

### Upholds the enterprise seam

`Tenant` leads every new sort key and every query; evaluation is per tenant;
retention is a policy env var (`AVURUOPS_RETENTION_ALERTS_DAYS`); storage stays
behind `storage.Store`. Rules are per-install config today; per-tenant rule
scoping and UI-authored rules couple to the v0.2 auth seam.

### Deploy (Helm)

`modules.alerting.enabled` (default true) + an `alerting:` values block (rules +
channels) rendered via `toJson` to a `-alerts` ConfigMap, mounted at
`AVURUOPS_ALERTS_CONFIG` and hot-reloaded — the exact pattern the service-health
`serviceGroups` config established. `values.schema.json` validates the shape
(known `when`, channel refs, URL format). The migrate Job runs `0008_alerts.sql`
only when the module is active.

### UI

`/alerts`: currently-firing alerts (target, since, rule, reason), a recent
history timeline, and the read-only rule list. Capability-gated via `ModuleGate`;
reuses the health status tones. Rules are edited in config, so the page teaches
that rather than offering an editor.

### Alternatives considered

- **Deliver from the gateway** — the gateway is an OTel Collector telemetry
  pipeline with no access to computed health or rule state; alerting is
  stateful control-plane logic that belongs with the health computation, in the
  hub.
- **Alert state in memory** — loses state on restart (re-fires, dropped
  resolves) and can't dedup; ClickHouse `ReplacingMergeTree` is the proven
  mutable-state pattern already in the codebase.
- **UI-CRUD rules in v1** — the write path exists (error-tracking triage), but
  "who may edit rules" needs auth (v0.2). Config-file rules ship now and match
  the health module; UI authoring lands with auth.
- **A general multi-signal rule engine now** — largest v1 surface; the pure
  `Evaluate` seam takes any `health.Report`-shaped input, so RED-threshold and
  error-tracking triggers extend it later without a rewrite.
- **Native Slack/email in v1** — a generic webhook already reaches Slack,
  PagerDuty, Teams, Opsgenie and Alertmanager; native formatters are additive
  `Notifier`s, not a v1 need.

### Documented v1 limitations

- **Single evaluator**: >1 hub replica duplicates notifications (no leader
  election yet). The evaluator logs that it is the active evaluator; operators
  running HA should keep hub replicas at 1 or wait for v2.
- **No silences**: a firing alert keeps its state until it resolves; there is no
  maintenance-window mute in v1.
- **Retention skew**: `alert_history` (30d) may outlive the traces that
  explained an alert; the UI links may dangle (same caveat as error-tracking).

## Verification

- **Unit** (`hub/internal/alerting`): the `Evaluate` state machine —
  ok→pending→firing→resolved, the `for` timer, dedup (no re-fire while firing),
  resolve-exactly-once, idle never fires, a cyclic/flapping input; config
  validation fail-loud; `webhookNotifier` against an `httptest` server (payload
  shape, retry on 5xx, **SSRF block** of a metadata IP, secret redaction).
- **Integration** (testcontainers ClickHouse): `alert_state` round-trip
  (Replacing keeps the newest), `alert_history` append + list; module gating
  leaves no tables and 404s the routes when off.
- **e2e** (compose + seed): seed a down group + a rule + a **local webhook
  sink** container; assert a fire POST lands with the right payload, then seed
  recovery and assert the resolve POST.
- **Playwright**: `/alerts` renders firing + history from seed; disabled-module
  path 404s / shows the off notice.
- **Helm** (`template-test.sh`): `alerting` in `AVURUOPS_MODULES`, the alerts
  ConfigMap + env + mount render, the whole surface disappears when disabled,
  and `values.schema.json` rejects a bad `when`.
- **Full gate**: `make check` (+ hub lint), `cd ui && npm run build`.
